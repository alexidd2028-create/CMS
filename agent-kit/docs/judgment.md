# 判斷力 rubric

> 這份檔案把「憑感覺」的決定換成可勾選的判準。遇到猶豫時，找到對應小節，照判準走。
> 每條都有正例（✅ 該這樣）與反例（❌ 不該這樣）。**例子是假想情境示範**，不對應本 repo 的真實檔案；驗收文件時不要拿例子裡的路徑查存在性。

## 1. 何時該升級模型（配合 delegation.md §5 的機械規則）

機械規則（錯一次/錯兩次）之外，出現以下任一訊號就**直接升級，不用等錯滿次數**：

- 任務需要在 3 個以上互相牽動的檔案間做取捨（例如改認證流程同時動後端 middleware 與前端狀態管理）。
- 你發現自己在兩個方案間反覆改主意超過一次。
- 問題涉及「沒有標準答案的設計取捨」而後果難以回退（資料 schema、對外公開的 API 介面形狀）。

✅ 正例：要改一個已有外部使用者依賴的公開 API 的參數形狀——這是介面設計 + 難回退，先派 `opus` 出方案再動手。
❌ 反例：改一個顯示文字的 typo 用 haiku 重試了三次——第一次錯就該升 sonnet，第三次還沒升是浪費兩輪。

## 2. 何時算「真的完成」

全部滿足才算完成，缺一項就還沒完成：

- [ ] 驗收條件逐條有證據（不是「應該可以」）。
- [ ] 跑過 project.md §驗證階梯 中適用的每一層，結果 0 error / 0 fail。
- [ ] `verifier` agent 回 `VERDICT: PASS`——改動超過 1 個檔案**或**超過 20 行時必要；更小的改動可免派 verifier，但驗證階梯照跑（此門檻與 CLAUDE.md 鐵律 6、delegation.md §6 一致）。
- [ ] 已 commit + push 到指定分支（`git status` 乾淨、`git log origin/⟨分支名⟩` 看得到；⟨⟩ 是佔位符，替換成實際分支名再執行）。
- [ ] 改動波及的文件（project.md、README）已同步。
- [ ] 回報裡寫明驗證做到第幾層、哪些沒驗到。

✅ 正例：「新增輸入驗證：改了 handler 與對應的表單元件共兩檔。驗證：測試 12 passed 0 failed、lint 0 error、verifier PASS（報告見下）。已推 commit abc1234。」
❌ 反例：「我已經修好了，程式碼看起來沒問題。」——沒有任何一項證據，這句話等於沒說。

## 3. 何時該停下來問使用者

**先查後問**：能用工具查到的（程式碼行為、文件、git 歷史）自己查，查不到再問。但以下情況**必須問，不准自己決定**：

- 不可逆或對外可見：刪除資料/檔案（超出自己本次建立的範圍）、force push、開 PR、merge、變更生產環境設定、需要使用者的 secret。
- 任務目標有兩種合理解讀且做錯要重來。「兩種合理解讀」的判定法：兩種解讀會動到的檔案集合明顯不同，或其中一種做下去難以回退——只是措辭不精確、做法殊途同歸的不算，直接挑合理的做。（例如「把介面改好用一點」——範圍完全開放，該問。）
- 發現使用者的前提是錯的（例如使用者說要改某個技術 X 的設定，但專案實際用的是技術 Y）——指出矛盾並問，不要默默照字面做。

✅ 正例：任務說「清掉沒用的設定項」但有兩個設定疑似被部署腳本間接使用——列出證據，用 AskUserQuestion 給選項。
❌ 反例：「要不要我繼續做下一步？」——下一步是原任務的自然延伸且可逆，這種問題不該問，直接做。（判準：**問「做不做」多半不該問；問「做哪一種」且差異重大才該問。**）

## 4. 什麼訊號代表方向錯了（該換路，而非重試）

重試 = 同方法再來一次；只有在「上次失敗原因是隨機的」（網路逾時、暫時性錯誤）時才合理。出現以下訊號代表**方法錯了**，重試是浪費：

- 同一個錯誤訊息出現第二次，內容一字不差。
- 每修好一處就冒出新的一處壞掉（打地鼠）——通常代表改錯了層，該往上找共同原因。
- 為了讓方案成立，需要的「例外」越來越多（第三個 special case 出現時停手）。
- 你開始想繞過驗證（跳過 lint、註解掉失敗的測試）——這是最強的紅燈，代表方案本身錯了。

換路的動作：停下 → 用一段話寫下「目前方法、失敗證據、猜測的根因」→ 換一個攻擊角度或按 delegation.md §5 升級。

✅ 正例：build 錯誤修了 import 又爆 export、修了 export 又爆型別——停下，發現真正原因是兩個模組循環引用，改結構一次解決。
❌ 反例：build 同一個錯誤跑了四次，每次只是加 `--force` 或刪掉快取重來——同方法重試超過兩輪，違反重試上限。

## 5. 品質底線怎麼驗（最低標準，低於此不准交付）

- **程式碼**：驗證階梯適用層全過；新程式碼沿用 project.md §慣例；沒有留下註解掉的舊碼或 debug 輸出。
- **文件/報告**：每個提到的路徑與指令都實際存在（用 Glob/Bash 驗過；本檔與 delegation.md 的假想例子除外）；沒有「保持高品質」這類無法執行的句子；弱模型讀一遍就知道下一步做什麼。
- **回報**：結論在最前面；證據用 檔案:行號；沒驗到的明說。
- **驗法**：自己對照上述清單一遍，然後派 `verifier`——兩者缺一不可，順序不可反（先自查省 verifier 的來回）。

✅ 正例：交付前發現報告裡寫的一個路徑 Glob 查無此檔（檔名記錯了）——修正後才交。
❌ 反例：報告裡寫「已全面測試」但實際只跑了 lint——這是品質底線最常見的死法：**用形容詞代替證據**。

## 6. 誠實條款：這套 rubric 補不了什麼

拆解、驗證、多樣本評審能把「執行品質」拉到接近強模型；但**模糊題與品味判斷**（UI 好不好看、文案語氣、產品取捨）沒有 rubric 能代替。遇到時按序處理：
1. 把模糊題轉成可比較的選項（做 2～3 個具體版本）；
2. 派 `opus` 當評審選優並給理由；
3. 仍不確定 → 用 AskUserQuestion 給使用者選項，明說「這是品味判斷，我的排序僅供參考」。
禁止：假裝品味判斷有客觀答案，或默默選一個不告訴使用者有其他選項。
