# 維護協議：怎麼安全地更新這套制度檔案

> 適用範圍：`CLAUDE.md`、`.claude/docs/*`、`.claude/agents/*`。
> 原則：事實跟著程式碼走（隨改隨更）；**規則**跟著使用者走（動之前先問）。

## 0. 改任何既有制度檔案前的固定流程

1. 備份：`cp <檔案> <檔案>.bak` 放到 scratchpad（**不要**把 .bak commit 進 repo；git 歷史是永久備份，.bak 只是本次作業的保險）。
2. 改完自查：改動處讀一遍，確認沒有跟同檔其他段落或 CLAUDE.md 鐵律矛盾。
3. 單獨 commit，訊息說明「為什麼改」而不只是「改了什麼」。

## 1. 可以自行改（不用問使用者）

- **project.md 的事實區**：程式碼變了就同步（這不只是允許，是 CLAUDE.md 鐵律 5 的義務）。
- **CLAUDE.md 的「踩坑記錄」區**：按 §3 格式追加。
- **diagnosis.md**：某條診斷的修法已落實、或發現新證據，可更新該條的狀態註記。
- **dispatch-templates.md**：新增模板、或在既有模板加一條驗收條件（刪驗收條件要問，見 §2）。
- 錯字、失效路徑、失效指令的修正（修正前用 Glob/Bash 驗證新值是對的）。

## 2. 動之前必須問使用者（用 AskUserQuestion，附上現行版本、提議版本、理由）

- CLAUDE.md 的**鐵律**：增、刪、放寬任何一條。
- delegation.md 的升降級規則與重試上限（這些數字是刻意保守的，放寬 = 制度退化的起點，見 letter.md）。
- judgment.md 的判準本身（例子可以換，判準不能自行改）。
- **刪除**任何制度檔案，或把規則從「必須」降為「建議」。
- verifier agent 的定義（弱化驗收者 = 弱化整套制度）。

## 3. 踩坑後教訓寫回哪裡、什麼格式

- **寫到**：CLAUDE.md「踩坑記錄」區最上方（新的在上）。
- **格式**（一行，三段式）：`- (YYYY-MM-DD) 坑是什麼——下次怎麼避開`。教訓必須是**可執行的動作**，不是感想。
  - ✅ `- (2026-07-02) README 曾寫 SQLite 但實際是 Postgres——信文件前先抽查一個關鍵事實對不對得上程式碼。`
  - ❌ `- (2026-07-02) 要更小心對待文件。`（沒有動作，不准寫這種）
- **什麼算值得記**：讓你浪費超過 3 次工具呼叫的誤解、violated 你預期的環境行為、使用者糾正過的做法。單純的程式 bug 不記這裡（那屬於 commit 訊息）。

## 4. 精簡規則（防止制度檔案自己變成 context 炸彈）

- **觸發點**：踩坑記錄超過 15 條，或 CLAUDE.md 超過 60 行，或任何單一 docs 檔超過 150 行。
- **做法**：把踩坑記錄中「已固化為規則」的條目刪掉（先確認對應規則真的已寫進對應檔案）；把過時條目移到 git 歷史（直接刪，git 留底）；合併重複。
- **精簡是改規則檔的一種**：CLAUDE.md 鐵律區與各檔的規則本體適用 §2（先問）；踩坑記錄與事實區適用 §1（自行做）。
- 精簡後派 `verifier` 確認：路由表指向的檔案都存在、被刪的內容確實已固化或過時。

## 5. 每季（或使用者要求時）的健檢清單

- [ ] project.md 抽查 3 個事實對照程式碼（依賴版本、檔案地圖、部署設定）。
- [ ] CLAUDE.md 路由表每個路徑 Glob 一次確認存在。
- [ ] delegation.md §3 的 model 清單對照當下 Agent 工具 schema 的 enum。
- [ ] 踩坑記錄是否觸發 §4 精簡。
