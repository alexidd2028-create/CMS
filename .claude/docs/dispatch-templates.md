# 派工 prompt 模板

> 用法：選對應模板 → 照抄 → 填 `⟨⟩` 空格 → 刪掉不適用的行（但三件套「目標與動機 / 驗收條件 / 回報格式」永遠保留）。
> agent type 與 model 的選法見 delegation.md §1、§3。模板裡的預設值可直接用。

## 1. 搜尋（找定義、找用法、找所有符合某模式的地方）

派給：`Explore`（model 預設即可）

```
搜尋任務。廣度：⟨medium｜very thorough⟩。
目標：找出 ⟨要找什麼，具體到可判定「找到/沒找到」⟩。
動機：⟨找到之後要拿來做什麼——讓你判斷邊界情況要不要算⟩。
範圍：⟨目錄或檔案 glob，例如 client/src/**。沒把握就寫「整個 repo，但跳過 node_modules、dist、package-lock.json」⟩。
驗收條件：
- [ ] 範圍內的相關命名變體都搜過（列出你用過的搜尋詞）
- [ ] 每個發現附 檔案:行號
- [ ] 一個都沒有時明說「未發現」，並列出搜過哪些詞證明找過
回報格式：條列 檔案:行號 + 一句話說明。不貼原始碼。最後一行寫你對「還有沒有漏網」的信心（高/中/低）與原因。
```

## 2. 實作（新功能、修 bug）

派給：`general-purpose`，model：`sonnet`（模式已完全明確的機械改動用 `haiku`）

```
實作任務。
目標：⟨要做什麼⟩。
動機：⟨使用者為什麼要這個——邊界情況照這個動機取捨⟩。
先讀：.claude/docs/project.md（專案事實與慣例）、⟨相關檔案路徑⟩。
做法提示：⟨已知的正確方向或範例位置；沒有就刪這行，讓它自己探索⟩。
限制：不改 ⟨不准動的檔案/行為⟩；遵守 project.md §慣例。
驗收條件（完成前自查）：
- [ ] ⟨可觀察的行為 1，例如「POST /api/entries/x 對缺 title 的請求回 400 { error }」⟩
- [ ] ⟨可觀察的行為 2⟩
- [ ] project.md §驗證階梯 適用層全過（列出你跑的指令與結果）
- [ ] 沒有殘留 debug 輸出或註解掉的舊碼
回報格式：改了哪些檔案（檔案:行號區間）、每條驗收條件 PASS/FAIL、驗證做到第幾層、做不到的明說。不貼大段程式碼。
```

## 3. 重構（行為不變，結構改變）

派給：`general-purpose`，model：`sonnet`

```
重構任務。鐵則：對外行為一個都不准變；發現「順手也該修」的 bug 只回報、不修。
目標：⟨結構要從什麼變成什麼⟩。
動機：⟨為什麼值得重構⟩。
範圍：⟨檔案清單。範圍外的檔案一律不碰⟩。
驗收條件：
- [ ] 重構前先記錄基準：跑 project.md §驗證階梯 適用層並記下結果
- [ ] 重構後同樣指令結果不劣化（lint/build 同樣 0 error）
- [ ] 所有呼叫端同步更新（用 Grep 證明沒有殘留舊引用，列出搜尋詞）
- [ ] diff 裡沒有行為變更（自己讀一遍 git diff 確認）
回報格式：變更摘要（一段話）、檔案清單、基準前後對照、發現但未修的 bug 清單（檔案:行號）。
```

## 4. 研究（查文件、比較方案、回答「該怎麼做」）

派給：`general-purpose`（Claude Code/API 相關改派 `claude-code-guide`）；高風險決策用 model `opus`

```
研究任務。只研究、不改任何檔案。
問題：⟨要回答的問題，一句話⟩。
決策背景：⟨這個答案會被拿來做什麼決定⟩。
必查來源：⟨官方文件 URL / repo 內的檔案；要求列出實際查過的來源⟩。
驗收條件：
- [ ] 每個結論附來源（URL 或 檔案:行號），查不到的標「NOT CONFIRMED」而不是猜
- [ ] 若是方案比較：各方案至少列一個具體缺點（沒有缺點的比較不可信）
- [ ] 給出明確建議與一句話理由，不要「各有優劣」收尾
回報格式：結論先行（建議 + 理由一句話），然後才是依據。全文不超過 30 行；更長的細節落檔到 scratchpad 回傳路徑。
```

## 5. 審查（驗收別人/自己完成的工作）

派給：`verifier`（自訂 agent，已設 sonnet + effort high）。若 verifier 不可用改派 `general-purpose` model `sonnet`，並把 `.claude/agents/verifier.md` 的規則整段貼進 prompt。

```
驗收任務。獨立驗證以下工作，不信任做事者的自述。
工作內容：⟨一段話說明做了什麼⟩。
驗收條件（逐條驗，每條要直接證據）：
- [ ] ⟨條件 1⟩
- [ ] ⟨條件 2⟩
- [ ] ⟨條件 3：通常包含「跑 project.md §驗證階梯 適用層」⟩
檢查範圍：⟨檔案清單或 git diff 範圍⟩。
回報格式：每條 PASS/FAIL + 證據（檔案:行號 或指令輸出摘要），最後 VERDICT: PASS/FAIL。FAIL 要指出差在哪，但不要動手修。
```

## 通用附則（適用所有模板）

- 一次派工一個目標。兩個目標 = 兩次派工（或先派第一個，拿到結果再派第二個）。
- 互不依賴的派工在同一個訊息裡並行發出。
- subagent 回報違反回報合約（貼了大段原文、沒逐條回驗收條件）→ 用 SendMessage 要求按格式重報，不要自己動手整理它的輸出。
- 派工前最後自查一次：「一個沒看過這個對話的人，只讀這段 prompt 能不能開工？」不能就是 context 給少了。
